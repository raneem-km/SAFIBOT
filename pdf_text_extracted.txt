SafiBot
Mini-Project Implementation Plan
Project type: AI + Knowledge Engineering + RAG web application
Target: SAFI Autonomous College
Primary goal: Help students find only the college information relevant to their course, department, semester and
interests.
1. Project Vision
SafiBot is a personalized college information assistant. College information can arrive through the public college
website, PDF notices, academic documents and announcements shared through WhatsApp. Students can miss
important information because it is fragmented across different sources. SafiBot collects approved information into
a knowledge base and lets students retrieve it through a web interface and natural-language chatbot.
Core principle: SafiBot is not just a PDF chatbot. It combines structured college data, document retrieval,
student-context rules and an LLM.

3. What NOT to Build for the Mini-Project
• Do not build real SAFI/university authentication or payment integration.
• Do not automatically read private WhatsApp groups.
• Do not build a full college ERP.
• Do not build native Android/iOS apps.
• Do not make WhatsApp/Telegram integration a dependency for the demo.
• Do not build complicated multi-agent workflows.
• Do not make website scraping mandatory; admin upload/paste must remain the fallback.

5. Why SQLite + ChromaDB?
SQLite is for structured facts. Examples: student profile, course, semester, event date, deadline, timetable
subject, exam time and room. These should be queried with normal database filters.
ChromaDB is for semantic document retrieval. A syllabus or regulation may contain many pages of natural
language. The document is split into chunks, embedded and stored in ChromaDB. A question such as “What is
Unit 4?” retrieves the relevant chunks before the LLM answers.
Important: Do not use ChromaDB for everything. Exam dates and timetable rows should be stored in structured
tables where possible; ChromaDB is mainly for unstructured document knowledge.

7. Data Model
Student: id, name, course, department, semester, batch, interests.
Notice: id, title, category, content, target course, target department, target semester, date, deadline, source,
source type, file path.
Event: id, title, description, date, time, venue, organizer, target course/department/semester, registration deadline,
source.
Document: id, title, document type, course, semester, department, file path, source, upload date.
Timetable row: course, semester, day/date, subject, time, room, document id/page.
8. Data Ingestion Strategy
Website: If SAFI's public website exposes useful announcements/events, optionally fetch public pages and
process new content. Keep this as an optional module because website structure can change.
WhatsApp: Do not attempt to read private WhatsApp groups. Instead, the admin can paste an announcement into
SafiBot. The system extracts event/deadline/eligibility fields.
PDF: Admin uploads syllabus, exam timetable, academic calendar, regulations or notices. The backend extracts
text and indexes it.
9. LLM Extraction for Announcements
Example input:
"Python workshop will be conducted Friday at 2 PM in Lab 3. BCA students can participate.
Registration closes Thursday."
Expected structured result:
{"type":"event", "title":"Python Workshop", "time":"14:00", "venue":"Lab 3",
"eligible_courses":["BCA"], "registration_deadline":"..."}
The admin should review the extracted fields and approve them before they become official SafiBot data.
10. RAG Pipeline for Syllabus and Documents
PDF → text extraction → clean text → chunks → embeddings → ChromaDB. When a student asks a question, the
system first applies profile/document filters, retrieves relevant chunks, then sends only those chunks plus the
question to the LLM. The response should include the document name and page number when available.
Example: BCA S3 student asks “Explain Unit 3 of Data Structures.” The retrieval layer prioritizes BCA S3 syllabus
content, finds relevant chunks, and the LLM explains them.
11. Large Exam Timetable Strategy
A large exam timetable may contain BCA, BBA, BCom and other courses. Do not make the LLM read the entire
PDF for every question. Extract timetable rows and associate them with course and semester. Store structured
rows in SQLite. Keep the original PDF and page number as the source.

12. Personalization / Knowledge Rules
A simple rule engine is enough for the prototype. If a notice/event has a target course and the student's course
does not match, hide it. Apply the same principle to semester and department. If an item has no target restrictions,
it can be treated as general college information.
Example rule: student.course in item.target_courses AND student.semester in
item.target_semesters → relevant

17. Implementation Order — Do This in This Order
Phase 1: Get the base project running. Inspect the chosen GitHub reference and understand its
React/FastAPI/RAG structure. Do not rewrite everything.
Phase 2: Create SQLite models for Student, Event, Notice, Document and Timetable.
Phase 3: Build a simple student profile and dashboard.
Phase 4: Implement PDF upload and PyMuPDF extraction.
Phase 5: Implement ChromaDB chunking/embedding/retrieval for syllabus and document Q&A.;
Phase 6: Implement structured timetable and exam timetable filtering.
Phase 7: Implement admin paste announcement → LLM extraction → review → save.
Phase 8: Implement personalization rules using course/department/semester.
Phase 9: Connect chatbot: determine whether a question needs structured DB lookup or RAG.
Phase 10: Add source/page information and test with the demo dataset.
Phase 11: Only if time remains: public website ingestion, OCR, reminders or Telegram/WhatsApp integration.

18. Minimum Demo Dataset
• 1–2 syllabus PDFs for BCA/BBA.
• 1 large examination timetable PDF containing multiple courses.
• 1–2 class timetable documents.
• 3–5 college notices.
• 5–10 event announcements, including WhatsApp-style text.
• 1 academic calendar.
• 1–2 placement/scholarship notices if available.
For data you do not have permission to use, create clearly labelled synthetic/demo records. Do not present
synthetic data as real SAFI announcements.
19. Final Demonstration Flow
• Admin uploads a large exam timetable PDF.
• System extracts/structures timetable information.
• A BBA S3 demo student logs in.
• Student asks: “When are my exams?”
• SafiBot returns only BBA S3 exams and cites the source.
• Admin pastes a WhatsApp-style Python workshop announcement.
• LLM extracts event details; admin reviews and publishes it.
• BCA students see the event according to eligibility.
• Student asks: “Explain Unit 3 of my syllabus.”
• RAG retrieves the correct syllabus chunks and the LLM answers with the source.
20. Evaluation for the Mini-Project
You do not need a large formal evaluation. Use a small manually verified test set.
• Information extraction accuracy: verify event title/date/time/venue/deadline against expected values.
• Personalization accuracy: verify that BCA/BBA/semester-specific information is shown only to intended students.
• Timetable retrieval accuracy: verify selected course/semester rows.
• RAG answer relevance: prepare 10–15 syllabus questions and manually verify answers.
• Source accuracy: verify that the cited PDF/page actually contains the answer.

22. Project Definition for Your Report
Suggested title: “SafiBot: A Knowledge-Driven Personalized College Information Assistant Using RAG and Large
Language Models”
Problem statement: Students receive academic information through multiple fragmented channels such as
websites, PDFs and messaging-based announcements. Because information is distributed and often contains
content for many courses and semesters, students can miss information relevant to them.
Proposed solution: SafiBot creates a structured and searchable college knowledge base, combines
metadata-based personalization with semantic document retrieval, and uses an LLM to provide natural-language
answers with source-backed information.

24. Final Guidance
Build the smallest complete version first. The most valuable prototype is one where an admin can add a
document/announcement, a student profile can be selected, and the student can successfully ask questions that
return personalized, source-backed answers. Once that works, add website ingestion or other integrations only if
time remains.
